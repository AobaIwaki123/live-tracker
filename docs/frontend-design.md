# Frontend Design Document

> 対象: `frontend/` 配下の React + TypeScript + Tailwind + shadcn/ui 実装  
> 現状の PoC を参考にしつつ、理想系を記述する。実装は下部のフェーズ表に従って段階的に行う。

---

## 1. アプリ全体の構造

### ページ構成

| パス | 役割 |
|------|------|
| `/` | 全アーティストの直近イベント一覧（メインダッシュボード） |
| `/artist/:id` | アーティスト個別のスケジュール一覧 |

**WHY** トップページを「アーティスト選択グリッド」から「全員の直近イベント一覧」に変える。  
→ ツールの本来の目的は「どのライブに行くか把握する」こと。選択肢を選ぶUI より、すべてのスケジュールが即座に見えるUIが正しい。  
**WHY NOT** アーティスト選択グリッドをトップにしない。選択肢が4グループ程度では中間画面として意味が薄く、1クリック余分に必要になる。

## 2. グローバルナビゲーション

### レイアウト

```
┌─────────────────────────────────────────────────────────┐
│  [Logo: ♪ Live Tracker]        [All] [Avam] [JJ] [...]  │
└─────────────────────────────────────────────────────────┘
```

- ロゴ: ♪ アイコン + "Live Tracker"（テキスト）、クリックで `/` へ
- アーティストタブ: `All` + 各アーティスト名をフラットに並べる
- モバイル: タブをハンバーガーに収納せず、横スクロール可能なタブバーにする

**WHY** アーティストをグローバルナビに出す。4グループ程度ならタブが最もアクセス効率が高い。  
**WHY NOT** ドロップダウンメニューにしない。ワンタップで切り替えられるフラットなタブの方が操作数が少ない。  
**WHY NOT** サイドバーレイアウトにしない。モバイル閲覧（電車でスケジュール確認）が主要ユースケースであり、縦スペースを節約すべき。

## 3. トップページ（All Events ダッシュボード）

### レイアウト

```
┌─────────────────────────────────────────────────────────┐
│ 2026年5月                                                │
│  ┌───────────────────────────────────────────────────┐  │
│  │ [avam] [アイコン]  5/10(日)  代々木第一体育館      │  │
│  │         Spring Live 2026 〜夢の続き〜    [5日後]   │  │
│  └───────────────────────────────────────────────────┘  │
│  ┌───────────────────────────────────────────────────┐  │
│  │ [jj]   [アイコン]  5/15(金)  Zepp Osaka           │  │
│  │         Juice=Juice Concert 2026         [10日後]  │  │
│  └───────────────────────────────────────────────────┘  │
│                                                         │
│ 2026年6月                                                │
│  ...                                                    │
│                                                         │
│ ── PAST ──────────────────────────────────────────── ▼  │
└─────────────────────────────────────────────────────────┘
```

### 詳細仕様

- **月区切りヘッダー**: `2026年5月` をセクション見出しとして表示
- **過去イベント**: 折りたたみ（デフォルト collapsed）で最下部に配置
- **各イベント行**: アーティスト識別色バー（左端） + アーティストアイコン + 日付 + 会場 + タイトル + カウントダウンバッジ
- **アーティスト識別**: 左端に4px の色バー + 小さいアーティストアバター（24px 円形）で識別

**WHY** 月ごとにグルーピングする。カレンダーアプリの慣例に合わせることで認知負荷を下げる。  
**WHY** カウントダウンバッジ（`5日後`）を必ず表示する。「いつ行くか」の判断に直結する情報であり、日付だけより意思決定が速い。  
**WHY NOT** カード型のグリッドにしない。イベントは「一覧で時系列を把握する」用途なので、密度の高いリスト形式が適切。グリッドは視覚的に豪華だが情報密度が低い。  
**WHY NOT** 過去イベントをデフォルト表示にしない。「これから行くライブ」が目的なので、ファーストビューにノイズを入れない。

## 4. アーティスト詳細ページ

### ヘッダー

```
┌─────────────────────────────────────────────────────────┐
│  ← Back                                                 │
│                                                         │
│  [アーティスト画像 横長バナー形式]                         │
│  ████████████████████████████████████████████████████  │
│  ████████████████████████████████████████████████████  │
│                                                         │
│  アーティスト名（大文字・太字）                            │
│  次のライブまで X 日 | 直近3ヶ月 N 件                     │
└─────────────────────────────────────────────────────────┘
```

- 画像: 円形アバターではなく **横長バナー（16:5 程度）**。画像のインパクトを最大化する
- オーバーレイ: 画像の下部に gradient overlay を重ね、その上にアーティスト名を表示
- サブ情報: 「次のライブまで X 日」「直近3ヶ月 N 件」をバッジで表示

**WHY** バナー形式を選ぶ。アーティストの顔写真・グループショットは横位置の構図が多く、4:3 や正方形より自然に収まる。  
**WHY NOT** 円形アバターにしない。グループのアーティスト写真を円形にトリミングすると顔が見切れることが多い。  
**WHY** 画像の上にテキストを重ねる。画像とメタ情報を分割すると縦スペースを2倍消費する。グラデーションオーバーレイで可読性を確保しつつ、コンパクトに収める。

### イベントリスト

```
┌─────────────────────────────────────────────────────────┐
│ Upcoming (5)                                            │
│ ──────────────────────────────────────────────────────  │
│                                                         │
│  MAY                                                    │
│  ┌──┬──────────────────────────────────────────────┐   │
│  │10│ Spring Live 2026 〜夢の続き〜                 │   │
│  │SUN│ 代々木第一体育館  18:00               [5日後] │   │
│  │  │ [チケットを取る]  [公式サイト]                │   │
│  └──┴──────────────────────────────────────────────┘   │
│                                                         │
│  ── PAST (8) ────────────────────────────────────── ▼  │
└─────────────────────────────────────────────────────────┘
```

- 日付ブロック: 日(数字) + 曜日(英語3文字)
- カウントダウン: `5日後` / `今日` / `明日` の優先表示、過去は `3日前` などグレーで
- チケットボタン: `ticket_url` がある場合のみ表示、ない場合はボタン自体を描画しない
- `fetch_status` バッジ: **ユーザーに表示しない**（内部実装詳細）

**WHY NOT** `fetch_status` をユーザーに見せない。`tier_1` / `tier_2` などはスクレイピングの内部状態であり、ユーザーにとって意味のある情報ではない。  
**WHY** チケットボタンを条件付きで表示する。ボタンを常時表示して無効化するより、存在しない機能を見せない方が混乱が少ない。

## 5. テーマ・カラーシステム

### アーティスト識別色

各アーティストに固定のアクセントカラーを割り当てる。`config/artists.yaml` に `theme_color` フィールドを追加する。

```yaml
- name: avam-fc
  theme_color: "#E91E8C"  # ピンク系
- name: jj
  theme_color: "#FF6B35"  # オレンジ系
```

フロントエンドでは CSS カスタムプロパティとして動的に注入する。

**WHY** 識別色を持たせる。アーティストが複数いるAll Eventsビューで、文字を読まなくても視覚的に「誰のイベントか」が分かる。  
**WHY NOT** ランダム生成やアバター画像からの自動抽出にしない。生成色は安定しないため、ユーザーの記憶に残るブランドカラーと一致しない可能性がある。手動で設定する方が信頼性が高い。

### ダークモード

- デフォルト: システム設定に追従（`prefers-color-scheme`）
- 手動トグル: ナビゲーションバー右端に配置
- 永続化: `localStorage` に保存

**WHY** ダークモードを実装する。夜のライブ帰りや暗い会場でスマホを確認する場面が多い。

## 6. イベントカード詳細仕様

### 情報の優先順位と配置

```
[左: 日付ブロック] [中: イベント情報] [右: カウントダウン]

日付ブロック (min-w: 56px):
  - 月 (英語大文字 3文字, text-xs, muted)
  - 日 (数字, text-3xl, bold, テーマカラー)
  - 曜日 (英語大文字 3文字, text-xs, muted)

イベント情報:
  - タイトル (text-base, semibold, 2行まで折り返し、それ以上は truncate)
  - 会場名 (MapPin アイコン + テキスト, text-sm, muted)
  - 開演時間 (Clock アイコン + テキスト, text-sm, muted) ← TBAなら非表示
  - [チケット] ボタン (Primary, ticket_url がある場合のみ)
  - [公式] ボタン (Outline, source_url がある場合のみ)

カウントダウン (right-align):
  - 今日: `TODAY` (赤バッジ)
  - 明日: `明日` (オレンジバッジ)
  - 2〜7日後: `X日後` (Primary バッジ)
  - 8日〜: `X日後` (Secondary バッジ)
  - 過去: `X日前` (muted, グレー)
```

**WHY** 日付ブロックを3行（月・日・曜）にする。曜日は「土日か平日か」の判断に必須だが、現在の実装では省かれている。  
**WHY NOT** 会場が「Venue TBA」と表示するテキストを使わない。情報がない場合はそのフィールドを非表示にする方が、偽情報より良い。

## 7. レスポンシブ方針

| ブレークポイント | レイアウト変更 |
|-----------------|---------------|
| `< 640px` (モバイル) | ナビタブ横スクロール / イベントカードを1カラム / ボタンを縦並び |
| `640px〜` (タブレット) | 基本的にモバイルと同一 |
| `1024px〜` (デスクトップ) | コンテンツ幅 `max-w-3xl` で中央寄せ、左右にパディング |

**WHY** `max-w-3xl` (768px) でコンテンツ幅を制限する。イベントリストは横に広げても情報量が増えない。テキストの行長を制限することで可読性を上げる。  
**WHY NOT** 2カラムグリッドにしない。時系列リストを横2列に並べると時間軸の認知が壊れる。

## 8. ローディング・空状態・エラー状態

### ローディング

- Skeleton ローダー: 現状の実装を維持
- ナビタブ: ロード中もタブ自体は表示（artist名は skeleton）

### 空状態（イベントなし）

```
　　　　　📅
　　イベント情報なし
　次のスクレイプ後に更新されます
　　　[公式サイトを確認する] → source_url へのリンク
```

**WHY** 空状態に公式サイトリンクを置く。イベントが取れていない場合でも、ユーザーが手動で確認できる導線を残す。

### エラー状態

- バックエンドが起動していない場合: 「バックエンドに接続できません。`uv run uvicorn src.web.app:app` を実行してください」と具体的なコマンドを表示する

**WHY NOT** 汎用的な "Something went wrong" だけ表示しない。このツールは開発者本人が使うため、具体的なデバッグ情報を出す方が有用。
