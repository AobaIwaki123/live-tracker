# 要件定義書 — idol-live-tracker

## 1. プロジェクト概要

アイドル・アーティストの公式 Web サイトからライブ・イベント情報を自動収集し、Notion データベースへ転記するツール。
新着イベントは Discord へ通知し、定期実行により常に最新状態を維持する。
人間は **base URL のみ** を指定すれば動作するよう、AI によるサイト構造解析フェーズを持つ。

---

## 2. 背景・目的

- 複数アーティストのライブ情報を手動で確認・転記するコストを削減する
- サイト構造（静的 HTML / JS レンダリング / 内部 API 等）を人間が網羅することは不可能なため、AI に解析を委譲する
- Notion 上で一元管理することでスケジュール把握を容易にする
- 新着情報を Discord でリアルタイムに受け取る

---

## 3. スコープ

| 区分 | 内容 |
|------|------|
| 対象 | 設定ファイルに列挙したアーティストの公式スケジュールページ |
| 対象外 | チケット購入・SNS 投稿 |

---

## 4. 機能要件

### FR-01: サイト構造解析（analyze フェーズ）

| # | 要件 |
|---|------|
| FR-01-1 | base_url のみを入力として受け取り、ページの Navigation 方式・HTML 構造・内部 API の有無を自動判定する |
| FR-01-2 | 判定した結果を `navigation` / `selectors` / `response` / `detail` セクションとして YAML 設定ファイルへ書き戻す（人間がレビュー可能） |
| FR-01-3 | `python main.py analyze [--artist NAME] [--force]` コマンドで実行できる |
| FR-01-4 | 解析には Claude API（claude-sonnet-4-6）を使用し、HTML・ネットワークキャプチャを LLM に渡して設定を生成する |
| FR-01-5 | 一度解析済みの設定は `analyzed_at` として日付を記録し、再解析は `--force` オプション時のみ行う |

---

### FR-02: ライブ情報スクレイピング（scrape フェーズ）

| # | 要件 |
|---|------|
| FR-02-1 | YAML の `navigation.type` に応じて URL リストまたはリクエストを自動生成し、将来 N ヶ月分のイベントを収集する |
| FR-02-2 | 取得できなかった項目は空文字扱いとし、処理を継続する |
| FR-02-3 | `python main.py scrape [--artist NAME] [--dry-run]` コマンドで実行できる |
| FR-02-4 | スクレイプ後に新規イベント・情報更新の両方を Discord へ通知する（FR-04 参照） |

**対応 Navigation タイプ**

| タイプ | 例 | 説明 |
|------|---|------|
| `single_page` | `https://example.com/schedule` | 全件が 1 ページに掲載 |
| `query_param` | `?d=2026-08-01` | クエリパラメータで月を切り替え |
| `path_segment` | `/schedule/2026/08` | URL パスに年月が入る |
| `pagination_links` | `<a class="next">` | HTML の次ページリンクを辿る |
| `api_endpoint` | `POST /api/schedule/get` | JS が内部 API を叩く（avam-fc.com 型） |

---

### FR-03: イベントデータ永続化

| # | 要件 |
|---|------|
| FR-03-0 | スクレイプ結果は常にローカル SQLite（`data/events.db`）へ書き込む（Notion 不要・オフライン動作の基盤） |
| FR-03-1 | Notion Integration Token と Database ID を `.env` で管理する（未設定時は Notion 書き込みをスキップ） |
| FR-03-2 | 下記スキーマに従い Notion DB へ書き込む |
| FR-03-3 | 重複判定キー `(グループ名, イベントタイトル, 開催日)` でレコードの存在を確認する |
| FR-03-4 | 新規イベントの場合はレコードを作成する |
| FR-03-5 | 既存イベントの場合、スクレイプ結果と Notion の値を比較し、**差分があるフィールドを上書き更新する**（スクレイプデータを正とする。手動入力も上書き対象） |
| FR-03-6 | 更新の有無に関わらず、スクレイプのたびに全イベントを再取得・比較する |
| FR-03-7 | AI エンリッチメント（FR-06）で補完されたフィールドも同様に上書き更新する |

**Notion DB スキーマ**

| プロパティ名 | 種別 | 用途 |
|---|---|---|
| イベントタイトル | タイトル | 公演名 |
| グループ名 | セレクト | アーティスト識別 |
| 開催日 | 日付（日時） | カレンダー表示・ソート |
| 開始時刻 | テキスト | カレンダー補足 |
| 会場名 | テキスト | 場所の把握 |
| 都道府県 | セレクト | 地域フィルタ |
| チケット URL | URL | 購入導線 |
| チケット料金 | テキスト | 予算管理 |
| 出演アーティスト | テキスト | 対バン情報 |
| ポスター画像 URL | URL | サムネイル |
| ソース URL | URL | スクレイピング元 |
| 取得ステータス | セレクト | 完全取得 / 一部未取得 / タイトル・日付のみ |

---

### FR-04: Discord 通知

| # | 要件 |
|---|------|
| FR-04-1 | Discord Webhook URL を `.env` で管理する |
| FR-04-2 | `scrape` 実行時に以下の2種類のイベントを通知する |
| | ① **新規イベント**: 初めて検出されたイベント |
| | ② **情報更新**: 既存イベントの空欄フィールドに値が追加された場合（例: 会場・チケット URL が coming soon から確定） |
| FR-04-3 | 通知メッセージの種別（新規 / 更新）をタイトルで明示する |
| FR-04-4 | 更新通知には**どのフィールドが追加されたか**を含める |
| FR-04-5 | 通知メッセージにはグループ名 / イベントタイトル / 開催日 / 会場名 / チケット URL / Notion ページリンクを含める |
| FR-04-6 | Webhook URL が未設定の場合は通知をスキップし、ログに警告を出す |
| FR-04-7 | 毎週月曜 09:00 JST に直近 2 週間のイベント予定をサマリーとして Discord へ送信する（フォーマットは `docs/discord-summary-format.md` 参照） |
| FR-04-8 | サマリーはローカル SQLite から読み込む。Notion の有無に関わらず動作すること |

---

### FR-05: 定期実行（cron）

| # | 要件 |
|---|------|
| FR-05-1 | macOS の cron（または launchd）を使い、任意のスケジュールで `scrape` コマンドを自動実行できる |
| FR-05-2 | 実行ログを `logs/` ディレクトリに日付付きで保存する |
| FR-05-3 | セットアップ手順を README に記載する |

---

### FR-06: Web インターフェース

| # | 要件 |
|---|------|
| FR-06-1 | React (SPA) によるモダンな閲覧インターフェースを提供する |
| FR-06-2 | **ホーム画面**: アーティスト画像が並ぶタイルビュー形式。画像は `img/` 配下のローカル画像を使用する |
| FR-06-3 | **詳細画面**: アーティストごとのイベントリストを時系列で表示する |
| FR-06-4 | **REST API**: FastAPI を使用し、SQLite (events.db) のデータを JSON 形式でフロントエンドへ提供する |
| FR-06-5 | **状態管理**: TanStack Query を使用し、効率的なデータ取得とキャッシュ管理を行う |
| FR-06-6 | **UI コンポーネント**: shadcn/ui を採用し、美しくレスポンシブな UI を実現する |

---

### FR-07: AI エンリッチメント（opt-in）

| # | 要件 |
|---|------|
| FR-06-1 | `python main.py enrich [--artist NAME]` コマンドで明示的に実行する（自動実行しない） |
| FR-06-2 | Notion DB の `取得ステータス: 一部未取得` または `タイトル・日付のみ` のレコードを対象とする |
| FR-06-3 | イベントタイトル・グループ名・開催日を組み合わせてチケットサイト（e+・チケットぴあ・ローソンチケット）を検索し、空欄フィールドを補完する |
| FR-06-4 | 補完できたフィールドのみ Notion レコードを上書き更新し、`取得ステータス` を更新する |
| FR-06-5 | 補完に Claude API（claude-sonnet-4-6）を使用する |

---

## 5. フォールバック戦略

```
Tier 1: 公式サイト メインページ（title / date）
       ↓ 空欄フィールドがある
Tier 2: 公式サイト 詳細ページ（venue / start_time / other_artists）
       ↓ まだ空欄がある → 取得ステータス: 一部未取得 として Notion 登録
Tier 3: AI エンリッチメント（enrich コマンドで opt-in 実行）
         e+ / チケットぴあ / ローソンチケットを検索して補完
       ↓ それでも取れない → 取得ステータス: 一部未取得 のまま保持
```

## 6. 非機能要件

| 区分 | 内容 |
|------|------|
| 実行環境 | macOS / Python 3.10+ |
| 依存ライブラリ | scrapling[all] / anthropic / google-genai / notion-client / python-dotenv / PyYAML / httpx（pyproject.toml で管理） |
| AI Provider | Claude API（claude-sonnet-4-6）または Gemini API（gemini-2.5-flash）のどちらか一方が使えれば動作する。環境変数 `AI_PROVIDER` で切り替え可能 |
| セキュリティ | 個人開発のため対象外（認証情報は .env で管理するのみ） |

---

## 7. 制約・前提

- 対象サイトの robots.txt は利用者自身が確認する
- Notion Integration は任意。未設定でも Discord 通知・ローカル SQLite 保存は動作する
- Discord Webhook は事前にサーバー設定で作成しておくこと
- `api_endpoint` タイプはリクエスト仕様が変更された場合は再解析が必要
